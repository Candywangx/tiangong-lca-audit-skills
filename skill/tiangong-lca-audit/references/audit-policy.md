# 审核判断政策

本文件定义所有过程与模型审核共同遵守的证据、严重程度和结论规则。

## 1. 证据优先级

1. **直接证据**：平台字段、输入/输出记录、模型结构、关联过程内容。
2. **跨字段证据**：多个窗口或多个关联过程之间可以直接验证的对应关系。
3. **规则依据**：本 Skill 的 `rules/*.json` 与审核方法。
4. **参考判断**：分类候选、行业常识和历史案例，只能帮助定位问题，不能单独证明问题。

每条审核发现至少需要一项直接证据。只有参考判断时，输出“需人工确认”。

规则中的 `standard_refs` 记录其对应的 CFIA-LCA-database-guideline 文件和章节，只作为规则依据锚点；审核输出不必逐条引用标准章节。若标准依据和本 Skill 规则发生冲突，先停止自动通过，按纠偏流程修正规则。

### 审核前题目查重关卡

- 每条待审核数据集（过程或模型）开始预检、source 核验和语义审核前，必须在平台同类数据集中分别按现有中文、英文题目（原始 `baseName`）精确搜索所有版本；对搜索结果核对完整题目和 UUID。不能只查当前审核队列，也不能把近似题目当作完全相同。搜索须能命中当前 UUID 和版本，以验证查询有效；搜索失败、结果被截断、题目缺失或无法读取候选时暂停审核，不得视为“没有重复”。
- 对题目完全相同、但 UUID 不同的每条候选，读取候选与当前数据集的完整原始 JSON 和版本并逐项比较；只忽略数据集自身的 UUID 身份字段，不忽略版本、交换、模型结构、来源和其他数据集内容。留存当前数据、候选原文、UUID/版本、比较结果与搜索证据。同一 UUID 的不同版本不触发本关卡。
- 若存在内容也完全一样的候选，立即暂停审核。人工确认具体候选及当前数据集后，记录确认人、时间、继续审核的决定和所确认的搜索结果，重新校验关卡后才可继续；确认前不得形成审核结论、生成最终报告或执行平台写入。题目相同但内容不同的候选可以继续审核，须保留差异记录；同题目本身不构成数据错误或自动驳回依据。

使用 Runtime 时，搜索及候选原文保存在案件的 `snapshots/title-duplicate-check.json`。只有收到人工明确确认后，才在 `agent-review/title-duplicate-confirmation.json` 记录 `decision: "continue"`、人工确认人的 `reviewer`、带时区的 `confirmed_at`、本轮 `search_fingerprint` 和全部内容相同候选的 `candidate_ids`（`UUID@版本`）。再次运行 intake 会重新搜索；候选、内容或搜索指纹改变时原确认失效，须重新确认。

## 2. 发现类型

| 类型 | 含义 | 是否影响通过 |
| --- | --- | --- |
| `blocking` | 已有充分证据证明存在关键缺失、错误或矛盾 | 是 |
| `advisory` | 不影响当前通过，但能提升清晰度、规范性或复用质量 | 否 |
| `manual_review` | 可能影响结论，但规则、分类范围或业务事实不足以确认 | 暂不自动影响 |
| `input_gap` | 缺少完成核心检查所需的数据 | 可能导致信息不足 |

发现类型可根据实际证据调整，不得仅沿用规则默认值。

## 3. 结论聚合

按以下顺序生成唯一结论：

1. 存在一条或以上已验证的 `blocking`：**不通过**。
2. 不存在阻断问题，但核心审核维度因 `input_gap` 无法完成：**信息不足**。
3. 不存在阻断问题和核心信息缺口，但存在可能改变结论的 `manual_review`：**需人工确认**。
4. 核心审核维度已完成且不存在阻断问题：**通过**。

只有 `advisory` 时仍可通过。

### 必审覆盖与不适用

- 必审清单只由 `rules/*.json` 的 `agent_review_required` 定义；模板、预检提示和语义审核使用同一目录。每项必审均须留下显式复核记录。
- 只有规则的 `allow_not_applicable` 为真，且已核查其 `condition` 和 `exceptions`，才可给出 `not_applicable`。记录必须包含可复核事实 `evidence`、具体证据引用 `evidence_refs` 和解释适用性边界的 `judgment`；字段非空只是准入条件，理由是否成立仍由 Agent 依证据判断，不得以字数或套话代替判断。
- 核心对象、类型、基准量和单位等检查不能用“不适用”跳过。缺证据、无法判断适用性时使用 `cannot_judge`，并保留信息缺口或人工确认，不得据此形成完整通过。
- 规则例外可以说明为何某项无需修改；未开放完整豁免的必审项仍须完成判断。DQR 等检查的局部范围例外只支持局部审查，不能替代完整数据质量检查或导出完整通过。

## 4. 必填与非必填

- 必填字段先检查是否存在，再检查内容是否正确。
- 非必填字段为空通常不产生发现。
- 非必填字段一旦填写，若与核心字段或输入/输出冲突，可以形成阻断问题。
- 某字段是否必填不明确时，不机械驳回；记录为人工确认。

必填性须对应当前对象类型与适用契约版本。接口要求某个键存在，不等于要求其值非空；页面的校验提示、隐藏字段或只读投影也不能单独证明提交内容有误。先区分提交内容确实缺失、当前视图未提供和审核工具获取失败，再按受影响维度判断。修复工具访问或补取审核材料的动作应指向审核侧，只有证据证明提交内容需要修改时才要求提交者修改。

## 5. 防止过严

- 分类没有完全契合项时，合理近似可以接受。
- 单元过程、单一操作或黑箱过程的 LCI 方法字段为空、`-` 或“不适用”通常可以接受；只有与数据集类型或正文冲突时才提出问题。
- `Calculated` 不等于不可追溯；已有来源或处理报告时，只核查关键计算是否需要补充。
- 已提供来源文献时，不得表述为“未标注来源”；继续核查时应准确指出缺失的是引用位置、数据处理说明，还是文献内容与数据集实际建模内容的区分。
- 来源文献的项目描述、参数和核算结论可以作为数据来源，但不得在未加区分时被当作当前数据集自身的描述、参数或结果。
- 平台动态生成的 LCIA 结果可能随背景过程链接、审核状态或平台计算更新而变化；默认不将其作为退回依据，也不要求提交者统一或重新计算该结果。只有审核任务明确要求核查计算结果且计算上下文稳定、完整时，才对其形成单独判断。
- 流的“未审核”状态不等于流内容错误。
- 产品流不等于基准流；非基准产品流未填写分配比例本身不构成问题，唯一基准流填写 100% 分配属于正常设置。
- 只看到部分窗口时，不得形成完整通过结论。
- 平台状态为“已通过”或存在历史通过记录，不等于本轮语义审核通过；仍需完成对象、类型、边界、功能单位或目标量、清单或模型结构、来源代表性和数据质量检查。
- 数据集类型是核心方法字段。`Partly terminated system`、`LCI result` 等类型必须有相应边界证据；没有证据时不得按字段值默认通过。

## 6. 发现记录结构

每条发现包含：

- `location`：窗口、字段、流或关联过程。
- `evidence`：输入中可复核的事实。
- `judgment`：为何构成问题或为何需确认。
- `severity`：四类发现之一。
- `impact`：是否影响通过及影响原因。
- `suggestion`：一句话可执行修改建议。
- `rule_id`：适用规则；没有明确规则时可为空。
