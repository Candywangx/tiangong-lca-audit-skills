# 输出契约

审核输出应让审核员能够复核，也让提交者知道如何修改。

## 1. 标准结构

```text
## 证据型报告

审核范围：
数据集类型：
输入充分性：
第一层 PDF/source 一致性：
第二层规则符合性：
审核结论：

阻断问题：
1. [位置] 问题与证据。影响：……。建议：……。

建议修改：
1. [位置] 问题与证据。建议：……。

需人工确认：
1. [位置] 待确认事项、原因和需要补充的证据。

信息缺口：
1. 缺失内容及其阻止完成的审核项。

结论说明：

## 平台退回意见
```

没有内容的分组可以省略。

审核结论必须先分为两个判断层，再给综合结论：

- 第一层 `PDF/source 一致性`：回答数据集字段、年份、名称、地点、技术路线、参考流等 claims 是否能被 PDF/source 原文语义支持，或是否存在直接冲突。该层必须由 Agent 阅读字段和 source 上下文后判断；不得用整段字段值字符串命中、关键词命中或程序规则作为最终结论。结论可为 `一致`、`未完全证实`、`不一致`、`证据不足`、`需人工确认`、`未核验`。
- 第二层 `规则符合性`：回答数据集是否符合机器规则和审核政策，包括阻断问题、建议修改、人工确认项和信息缺口。结论可为 `符合规则`、`基本符合规则，有建议修改`、`不符合规则`、`规则证据不足`、`需人工确认`。
- 综合结论根据两层结论和 findings 聚合为 `通过`、`不通过`、`信息不足` 或 `需人工确认`。source 字段 `not_found` 不能自动等同于数据错误；只有直接冲突或规则阻断才进入不通过判断。

输出视图必须分为两类：

- `## 证据型报告` 面向审核员复核，可以保留规则编号、证据边界、信息缺口和人工确认项。
- `## 平台退回意见` 面向提交者修改，只写可定位、可执行的意见；证据不足或仅用于限制结论的信息缺口不得写成绝对结论。

source 核验结果在证据型报告中应写明 source ID、文件、页码或表名、核验字段、状态、摘录和一句判断理由。涉及表格或数值时，还应写明原始单位、原始值、目标字段和换算链；缺少附录/source table 时，应列出缺失字段而不是只写“需要 source”。source 与数据集字段存在直接冲突时，可形成需修改的意见；已确认提交资料缺少核心依据时，可要求补充具体资料，但不能等同于数据错误。source 不可用、抽取失败或字段未命中通常只限制审核结论，是否要求提交者补充材料须按第5节判断。

## 2. 批量审核与案件存档

- 批量任务必须遵循“一条数据集一份独立 Markdown 审核报告”；每份报告只包含该数据集的证据、发现、结论和平台意见。
- 可以额外生成批次汇总索引，但汇总索引不能代替独立报告，也不能把多条数据集的平台意见合并为一份报告。
- 每条数据集应独立存档完成审核所使用的原始输入或平台响应，包括审核任务、数据集详情和实际引用的关联流或关联过程。
- 存档用于后续复核、人工纠偏和回归评测；真实平台数据遵守仓库隐私要求，不进入 Skill，也不得提交。
- 审核报告和存档在未经人工确认或纠偏前，不得直接作为训练真值，也不得据此自动升级通用规则。
- 无法取得数据集详情时，仍为该任务生成独立报告并存档现有任务证据，结论按输入充分性规则处理。

## 3. 写作要求

- 先写事实，再写判断。
- 一条发现只表达一个可执行问题；同一根因不要拆成多条。
- 修改建议尽量控制为一句话，并明确修改字段或核查动作。
- 对学习者解释关键逻辑，但不写长篇 LCA 教程。
- 不使用“请规范填写”“请检查”等无法执行的空泛表述。
- 不使用“明显”“大量”“严重”等无判定标准的程度词；直接陈述冲突事实，能够量化时给出差值、比例或适用阈值。
- 不输出内部推理、置信度或为了凑数生成的问题。

## 4. 通过说明

通过时仍需概括：

- 数据集对象与边界。
- 功能单位、基准流或模型目标。
- 清单或模型结构完整性。
- 来源与代表性。
- 单位、分类和管理信息的总体情况。

通过说明不是正式签字。正式通过报告草稿使用 `assets/approval-report-template.md`。

## 5. 平台意见

每份审核报告末尾必须包含 `## 平台退回意见`，用于提供可直接复制到天工平台的审核文字；该部分只能来自前文证据型报告中的发现。严重程度和结论仍以 `audit-policy.md` 为准，本节只定义面向提交者的标识、选择和写法。

`## 平台退回意见` 整段最终输出不得超过 1000 字，计入标题、编号、标识、标点、空格和换行。超过时应合并同根问题、精简表述后重新检查；不得截断文本或省略已验证的阻断问题。仍无法在限额内保留必要证据和修改动作时，应停止生成平台意见并交由审核员处理，不得输出超限稿。

### 标识与排序

使用 `①②③……` 连续编号，每条意见独立成段，编号后必须紧接下表中的标识。按表中顺序排列，同类中先写对建模结果影响更大的问题；编号和排序不能代替标识。

| 已核定的发现类型 | 必须使用的标识 | 提交者应理解的含义 |
| --- | --- | --- |
| `blocking` | 【需修改】 | 已证实的错误、矛盾或关键缺失，影响通过，必须解决。 |
| `input_gap` | 【需补充】 | 缺少完成核心审核的必要依据，补齐前无法完成判断；不等同于已证实错误。 |
| `manual_review` | 【需确认】 | 尚未定论的疑点，需要核实；暂不作为已确认的阻断问题。 |
| `advisory` | 【建议优化】 | 不影响当前通过的改进。 |

- 标识必须取自实际发现的严重程度，不能根据“补充”“确认”“建议”等动词推断，也不能因为整份报告不通过而升级其他意见。
- 已证实缺少必要蒸汽投入，即使修改动作是“补充蒸汽”，仍使用【需修改】；缺少运输距离的核心依据才可能使用【需补充】。
- `cannot_judge` 只允许空严重程度、`manual_review` 或 `input_gap`；不能同时宣称已确认阻断或只是建议。空严重程度、未命中字段不能自动变成【需补充】。应先判断是否存在真实的核心信息缺口，未核定前只留在证据型报告。
- 不省略任何已验证的阻断问题；人工确认、建议项只保留提交者能够具体处理的事项。
- 不得把工具读取失败、附件抽取失败、权限受限或页面展示限制直接写成提交者的数据错误或补交义务。只有核实提交资料确实缺少核心依据，且能说明补什么、用于哪项审核时，才使用【需补充】；也允许提交估算依据，不默认要求原始实测记录。
- 没有可执行意见时写“无”。结论为通过但有建议项时，标识仍为【建议优化】，不得暗示必须退回。

### 面向提交者的写法

- 每条按“位置 + 可见证据 + 问题判断 + 明确修改建议”组织，通常用两到三句讲清“哪里有问题、为什么、怎么改”。不机械拼接审核笔记，不为了限字数删掉决定判断的条件。
- 直接使用页面中的字段名、流名称、分类和数值，使提交者能够定位问题。数字必须带对应物料或字段名称及单位，不写需要反查的斜杠数字串。
- 技术术语先用中文说明；必须保留的页面选项可写成“单一操作（Unit process, single operation）”。避免只说“聚合边界”“角色错配”“归属口径”“终止范围”等抽象结论。
- 当问题来自底层清单但可能未在页面正常展示时，明确写出交换方向、数量和流名称；不得用未经说明的工艺角色推断替代可见证据。
- 当问题来自 source 核验时，写出来源名称、页码或表名以及与当前字段的具体差异；同名来源才补足区分信息，不用孤立UUID代替可读来源名称。
- 存在同名数据集时，争议交换必须同时核对数据集 ID、版本、交换方向、数量和流名称；报告抬头应有完整身份，意见中仍需写清争议流和数值，不能仅凭数据集名称或近似数值判断。
- 能确认修改目标时，直接说明把哪个字段改为什么；无法确定唯一答案时，说明需要核实什么、依据什么选择。不得给出未经证实的唯一分类或数量。
- 流分类或已审核流需要修改时，应写明实际检索到的候选分类路径或候选范围；无法确认唯一候选时，写明候选范围、需核实条件，以及“找到合适分类或者采用‘新增版本号’的方式对流分类进行修改”。
- 同一根因、同一严重程度的意见合并，并保留全部证据关联；不同严重程度的事项分开。不得靠取最高严重程度把建议项包成必须修改。
- 不使用“blocking”“规则编号”等内部审核标签，不使用 Markdown 加粗、子项目符号、表格或需要二次整理的字段式结构。上表中的四类标识必须保留。
- 不写空泛的“请检查”“请规范填写”；必须说明需要核实或修改的具体内容。不指责提交者，不把未确认的问题说成确定错误。
- 平台意见必须忠实于前文审核发现，不新增没有证据支撑的问题；历史已改、未改和新发现的分类仍在证据型报告中保留。

### 本地改写稿与生成

使用 Runtime 时，将经复核的自然语言意见保存到案件的 `agent-review/platform-opinions.json`，内容为 `{"items": [...]}`。每条只保留 `severity`、不带编号及标识的 `text`、`finding_refs`；引用写成案件相对文件 `path` 和零起算 JSON `pointer`，例如 `agent-review/agent-findings.json` 的 `/rule_reviews/0` 或 `/additional_findings/0`。程序按已关联发现验证严重程度，再统一添加标识和排序，不根据正文猜测判断。

同根来源或预检发现可通过 `source-checks/checks.json` 的 `/0` 或 `precheck/precheck.json` 的 `/findings/0` 一并关联；所有引用必须存在且与该意见同级。不得为了省略意见随意修改来源状态或原严重程度。若自动来源冲突的默认分级与已有效的 Agent 复核不一致，应在对应 source check 的 `extra.reviewed_severity` 和 `extra.reviewed_finding_ref` 明确引用该判断，保留原证据；只接受有效 `fail` 规则或已校验附加发现中核定的阻断或建议级别，未定论的 `cannot_judge` 不得作为降级依据。

`semantic-review` 将同一份改写稿用于自动报告和本地平台结果导出；独立报告和意见草稿须同步使用该文字。无效引用、文本自带标识或严重程度不一致时生成失败；遗漏的阻断项仍会保留在自动输出中，必须进一步复核并改写，不能靠作者稿掩盖。自然语言仍由 Agent 编写和复核，程序不自动改写事实或制造修改建议。

### 输出前复核

逐条核对标识与原始发现、证据与修改动作；同一意见在独立报告、自动报告和本地意见草稿中应一致。缺标识、标识与严重程度不符、遗漏阻断问题、同根重复或引用失效时，不得作为完成稿交付。程序负责检查标识、排序和证据关联，Agent另行复核自然语言是否清楚、条件和单位是否完整。

示例（不同发现，不表示必须同时出现四类意见）：

```text
## 平台退回意见

①【需修改】“年产量”填写为8,000,000 kg/年，而引用项目报告表2中的产量为800吨/年，即800,000 kg/年，相差10倍。若采用该项目数据，请改为800,000 kg/年；若采用其他生产规模，请提供对应依据并说明。

②【需补充】“数据来源”目前只有格式说明，无法说明运输距离和接收量的依据。请补充对应记录或估算过程，并注明用于当前数据的数值；补齐前无法完成数据来源审核。

③【需确认】参考年份与引用报告的发表年份不同。请说明数据实际对应哪一年；如果进行了年份调整，请提供调整方法，不能仅凭发表年份不同认定填写错误。

④【建议优化】英文路线描述重复了三次。请保留一段，并统一中英文对运输起点的描述。
```
